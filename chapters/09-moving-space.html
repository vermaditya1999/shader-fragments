Moving space: translate, rotate, scale

In p5.js you call translate() and rotate() and the drawing moves. A shader can't move a shape, because there's no shape object to move, only pixels asking questions. So instead you move the question: each pixel transforms its own coordinates before asking. This chapter explains why that runs backwards, builds rotation from the unit circle, and ends with a 2D camera.

9.1Move the space, not the shape

Every SDF from Chapter 8 describes a shape sitting at the origin. To draw a circle at the point c instead, each pixel asks the origin-circle a modified question: "if c were the origin, where would I be?" That's p - c (Chapter 7's arrow from c to the pixel). So the circle at c is sdCircle(p - c, r).

Notice the minus sign: to move the shape right by c, you move the coordinates left by c. Every transform works this way round, because you're applying it to the pixel's coordinates, not to the shape:

Scaling feels backwards at first. Dividing coordinates by 2 means the pixel that's 1 unit from the center now asks "am I inside?" with the coordinates of a point 0.5 from the center. The shape's edge, once at 0.5, is now reached by pixels at 1.0, so the shape looks twice as big.

There's one more detail with scaling. After dividing by s, the SDF returns a distance measured in the shape's own (scaled) units. Multiply it by s to get back to real distance, or your smooth edges, outlines and glows will come out the wrong width:

Delete the * s. What happens to the bands as the box grows and shrinks?

The shape is still drawn in the right place at the right size, because the sign of d hasn't changed. But the bands stretch apart when the box is big and bunch together when it's small, because the distances are now in box units, not real units. The white edge line also gets thicker and thinner. Anything that relies on the distance being real (edges, outlines, glows, and 3D raymarching later) goes wrong.

9.2Rotation, from scratch

Moving and scaling are simple arithmetic. Rotation needs the one piece of real derivation in this chapter, and you already know everything it uses.

Any point (x, y) can be read as a recipe: "x steps along the x axis's arrow (1, 0), plus y steps along the y axis's arrow (0, 1)". Now rotate the whole plane by an angle θ. The plane turns rigidly, like a sheet of paper pinned at the origin, so the recipe still holds: the rotated point is x steps along the rotated x arrow plus y steps along the rotated y arrow. So you only need to know where the two axis arrows go:

  • The x arrow (1, 0) is the point at angle 0 on the unit circle. Turned by θ, it's the point at angle θ: (cos θ, sin θ), straight from Chapter 5.
  • The y arrow is always a quarter turn ahead of the x arrow, and Chapter 7's quarter-turn trick turns (cos θ, sin θ) into (−sin θ, cos θ).

Put the recipe together:

rotated = x · (cos θ, sin θ) + y · (−sin θ, cos θ) = (x cos θ − y sin θ, x sin θ + y cos θ)

In GLSL, as a function (angles in radians, positive turns counterclockwise):

vec2 rotate(vec2 p, float a) {
    float c = cos(a), s = sin(a);
    return vec2(c * p.x - s * p.y, s * p.x + c * p.y);
}

And because transforms run backwards, to turn a shape by a, you turn the coordinates by −a: sdBox(rotate(p, -a), size).

Notice the whole distance field turns with the box, bands and all. Rotation doesn't stretch anything, so distances stay real and nothing needs correcting. (That's also why the dot product, which only depends on lengths and angles, doesn't change under rotation, as promised in Chapter 7.)

9.3The same thing, as a matrix

You'll see rotation written with mat2 everywhere. A matrix here is just a compact way to store "where the axis arrows go". A mat2 holds four numbers as two columns, and each column is an arrow:

float c = cos(a), s = sin(a);
mat2 m = mat2(c, s,        // first column:  where the x arrow goes
              -s, c);      // second column: where the y arrow goes
vec2 rotated = m * p;      // = p.x * (first column) + p.y * (second column)

Multiplying a matrix by a vector, m * p, means exactly the recipe from before: p.x steps along the first column plus p.y steps along the second. So a matrix isn't new math; it's the recipe, packed into a value you can pass around and reuse.

Watch out: columns, and which side the vector is on

GLSL fills a matrix column by column, so the first two numbers you type are the first column. Read across a line of code and it looks like a row, which trips everyone up.

And the order of multiplication matters: m * p uses the columns, but p * m uses the rows, which for a rotation matrix turns the other way, by −a. That's why you'll see Shadertoy code write p *= rot(a) (meaning p = p * rot(a)), which turns the coordinates backwards and so turns the shape forwards. If a shape spins the wrong way, flip the sign of the angle.

Matrices can do more than rotate. Any two columns describe some way of moving the axis arrows: mat2(2.0, 0.0, 0.0, 1.0) stretches x by 2, and mat2(1.0, 0.0, 0.5, 1.0) leans the y arrow sideways (a shear). Rotation is the special case where both arrows stay length 1 and at right angles.

9.4Order matters: spin or orbit

Combining a move and a turn gives different results depending on the order. Both panels below use the same box, the same offset (0.5, 0) and the same angle, in opposite orders:

Read each line from the pixel's point of view, left to right:

  • Left, rotate(p - offset, -t): first measure from the offset point, making it the origin, then turn around that origin. The box stays at the offset and spins in place.
  • Right, rotate(p, -t) - offset: first turn the whole space around the canvas center, then measure from the offset. The offset point itself is carried around by the turning space, so the box orbits the center, always keeping the same side toward it, like the Moon.

To rotate a shape around some pivot point, measure from the pivot, rotate, and (if you want to stay in the same coordinates) add the pivot back: rotate(p - pivot, -a) + pivot. 9.5Transforms inside transforms: a solar system

Positions can also be computed forwards, the normal way round: rotate a point to find where a planet is, then draw a circle there with length(p - planet). This works nicely for circles, which look the same from every angle. Stacking these gives a hierarchy, where each object moves relative to its parent: a moon circles a planet that circles the sun. The moon's position is the planet's position plus its own rotated offset, so it inherits all the planet's motion. That's a hierarchy of transforms, the same idea as nesting push() and pop() in p5.js. The light math runs in linear values and gets tone mapped and gamma corrected at the end, exactly as Chapter 6 recommends.

What you now know

  • Shaders transform the coordinates, not the shape, so everything runs backwards: move by c with p - c, scale by s with p / s (then multiply the distance by s), turn by a by turning p by −a.
  • Rotation: the x arrow goes to (cos θ, sin θ), the y arrow to (−sin θ, cos θ), and the point keeps its recipe: (x cos θ − y sin θ, x sin θ + y cos θ).
  • A mat2 stores two columns, the new x and y arrows. m * p uses them; p * m turns the other way.
  • Order matters: move-then-turn spins in place, turn-then-move orbits.
  • Draw shapes in their own coordinates and transform the question. Transforms can nest into hierarchies.
  • A camera is one transform from screen to world at the top of mainImage.
