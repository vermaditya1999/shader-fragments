How the GPU runs your shader

You've been writing mainImage and trusting that something calls it once per pixel. This chapter opens the box: what the graphics card actually is, the path from a triangle to a colored pixel, what the workbench wraps around your code, why an if can cost you both branches, and why numbers on a GPU aren't quite the numbers from math class.

17.1A few professors, or a stadium of students

A CPU, the main processor, has a handful of very fast, very clever cores. Each one can follow a long, twisting chain of steps where every step depends on the last: running your browser, your operating system, a game's rules. Think of a few brilliant professors.

A GPU, the graphics processor, has thousands of simpler cores. Each is slower and less clever than a CPU core, but they work together on one kind of job: the same small program, run on huge amounts of data at once. Think of a stadium full of students, each given one sum to do, all doing it at the same moment.

A 1920 × 1080 canvas has about two million pixels. At 60 frames per second, that's about 124 million calls to mainImage every second. No CPU could keep up, but each call is independent of the others, which is exactly the shape of work a GPU is built for. That independence is also why a shader can't look at its neighbors' results or remember anything (until Chapter 15's trick): every pixel is computed by a different student who can't see anyone else's paper.

17.2The pipeline: from triangles to pixels

GPUs were designed to draw 3D models made of triangles. Every drawing goes through the same fixed sequence of stages, called the graphics pipeline:

  1. The program hands the GPU a list of vertices, the corners of triangles.
  2. The vertex shader runs once per corner and says where on screen it lands. In a 3D game, this is where models get rotated, moved and put into perspective.
  3. The rasterizer, fixed hardware, works out which pixels each triangle covers.
  4. The fragment shader runs once for each covered pixel and returns its color. ("Fragment" because a pixel-sized piece of a triangle isn't yet a final pixel: in 3D, several triangles may cover the same spot, and only the nearest wins.)
  5. The colors land in a framebuffer: the screen, or a texture (Chapter 15).

Everything in this course has been a fragment shader. So how do you get one to run on every pixel? Draw a single triangle big enough to cover the whole screen.

17.3The full-screen triangle

The vertex shader places corners in clip space, a coordinate system where the visible screen always runs from −1 to 1 in both x and y, whatever its size in pixels. Anything outside is clipped away. One triangle with corners at (−1, −1), (3, −1) and (−1, 3) is big enough that the square −1..1 fits entirely inside it:

(Two triangles making a rectangle work too, and many runners use them. One triangle is slightly cheaper, because GPUs shade pixels in small groups, and groups straddling the diagonal seam between two triangles get shaded twice.)

Here is the entire vertex shader this site uses. It receives each corner's position as an input called an attribute and passes it straight through:

#version 300 es
in vec2 aPos;                                     // this corner's position: (-1,-1), (3,-1) or (-1,3)
void main() { gl_Position = vec4(aPos, 0.0, 1.0); }   // already in clip space: pass it on

17.4What the workbench wraps around your code

A WebGL fragment shader doesn't have mainImage, fragCoord or iTime. Those are Shadertoy's conventions, and every runner, including this site's, makes them work by gluing a few lines above and below your code before compiling it. Here's the glue, exactly:

#version 300 es                  // which version of GLSL: "OpenGL ES 3.0", which WebGL2 uses
precision highp float;           // use full 32-bit precision for floats (see below)
precision highp int;
precision highp sampler2D;
uniform vec3 iResolution;        // every i-name is a uniform the runner fills in each frame
uniform float iTime;
uniform float iTimeDelta;
uniform int iFrame;
uniform vec4 iMouse;
uniform vec4 iDate;
uniform sampler2D iChannel0;
uniform sampler2D iChannel1;
out vec4 sf_FragColor;           // the real output of the fragment shader

// ... your code goes here, including mainImage ...

void main() {                    // the real entry point: GLSL always starts at main()
    vec4 c = vec4(0.0, 0.0, 0.0, 1.0);
    mainImage(c, gl_FragCoord.xy);        // gl_FragCoord: this pixel's center, built in
    sf_FragColor = vec4(c.rgb, 1.0);
}

So fragCoord is simply gl_FragCoord.xy, which the rasterizer provides: the pixel's center, in pixels, with (0.5, 0.5) at the bottom-left (Chapter 3). And when an error message mentions a line number, the workbench subtracts the 13 lines of glue above your code, so the number matches what you see. Chapter 18 builds a runner that does all this in about 100 lines of JavaScript.

17.5Four ways data gets in

  • Attributes: values attached to each vertex, like aPos. Only the vertex shader sees them.
  • Varyings: values the vertex shader outputs per corner, which the rasterizer smoothly blends across the triangle for each pixel (a mix between three corners). In 3D rendering they carry things like texture coordinates. Our full-screen shaders don't need any, since gl_FragCoord already says where each pixel is.
  • Uniforms: values that are the same for every vertex and pixel in one draw, set by JavaScript before drawing. iTime, iResolution and iMouse are uniforms (Chapter 1).
  • Textures: images the shader can read anywhere (Chapter 15).

And one way out: the fragment shader's out vec4, one color per pixel, written to its own pixel only. A shader can read from anywhere in a texture, but it can only write to the pixel it was called for. That asymmetry shapes every technique in this course: it's why Chapter 15's dye had to look upstream instead of pushing downstream.

17.6Lockstep: why an if can cost both branches

The thousands of GPU cores aren't fully independent. They're organized in groups, typically of 32 or 64 (NVIDIA calls them warps, AMD wavefronts), and every core in a group executes the same instruction at the same time, each on its own pixel. This is called SIMT: single instruction, multiple threads. It's what makes GPUs so efficient: one instruction decoder drives dozens of calculators.

Now consider an if. If every pixel in a group takes the same branch, there's no problem. But if some go one way and some the other, the group can't split up. It runs the first branch with the other pixels switched off, then the second branch with the first ones switched off. The group pays for both:

This is called divergence, and it has practical consequences:

  • A branch that's the same for every pixel (it depends only on uniforms, like if (iTime > 10.0)) costs nothing extra.
  • A branch that differs between neighboring pixels costs roughly both sides wherever the boundary passes. Usually that's fine; it only matters when both sides are expensive.
  • Loops are the big one. A group can't finish until its slowest pixel finishes. Chapter 13's step heat map showed that rays grazing an edge need the most steps, and every group along an edge waits for them.

Groups are built from little 2 × 2 blocks of pixels called quads, and that's the secret behind Chapter 8's promise. dFdx(v) is simply the difference between v in this pixel and in its horizontal neighbor within the quad, dFdy(v) the vertical one, and fwidth(v) is abs(dFdx(v)) + abs(dFdy(v)). Neighbors running in lockstep can compare notes for free.

17.7Numbers on a GPU: floating point

A float is stored in 32 bits, like scientific notation in binary: about 7 significant digits, times a power of two. That has a consequence you can see: the bigger a number is, the coarser the steps between the numbers a float can represent. Near 1 the gap between neighboring floats is about 0.0000001; near 1,000 it's about 0.00006; near 10,000 it's about 0.001.

This example draws the same smooth ramp four times. Each strip computes it from a number that changes by only 0.001 across the strip, but sitting at a different size: near 1, 100, 1,000 and 10,000:

Near 1 the ramp is smooth. Near 100 it's faintly stepped, near 1,000 it's a staircase, and near 10,000 there are only a couple of steps left: the float simply can't hold "10000.000417". Real shaders hit this in three common ways:

  • iTime grows. After a few hours, sin(iTime * 50.0) gets choppy, because iTime is large and its fine detail is gone. Shaders that must run for days use mod(iTime, period).
  • Far from the origin. Coordinates of 100,000 in a 3D world lose the precision to place small details, which is why terrain flights eventually jitter.
  • The sine hash. Chapter 11's fract(sin(x) * 43758.5453) multiplies by a large number on purpose; with large inputs it runs out of digits and starts showing patterns.

The precision highp float line in the glue asks for full 32-bit floats. Older mobile GPUs also offered mediump, often 16-bit with only about 3 significant digits, which is why that line matters.

When math breaks: NaN and infinity

Some operations have no real answer. Dividing a positive number by zero usually gives infinity. The square root of a negative number, log of a negative number, 0.0 / 0.0, or pow of a negative base are officially "undefined" in GLSL, and on most GPUs that means NaN, "not a number". NaN is contagious: anything computed from it is also NaN, and every comparison with it is false. What NaN looks like on screen isn't defined: often black, sometimes garbage, and it can differ between GPUs, which makes it a classic "works on my machine" bug.

Chapter 19 turns this into a habit: when something is mysteriously black, check for NaN first.

17.8What makes a shader slow

The cost of a frame is roughly number of pixels × work per pixel. Some rules of thumb follow from everything above:

  • Resolution counts twice. Halving the width and height quarters the number of pixels. That's why the workbench quietly lowers its resolution when a shader runs slower than about 28 frames per second, and why a heavy shader can be lovely at a small size and stutter full-screen.
  • Loops multiply everything inside them. A raymarch of 100 steps calling a map with an fBm of 6 octaves is 600 noise evaluations per pixel, and the normal calls map six more times. Fewer steps, fewer octaves, or a cheaper map make a big difference.
  • The slowest pixel sets the pace for its group, so expensive work along edges and in grazing rays dominates.
  • Exit early. Break out of loops as soon as the answer is known, and skip expensive lighting for pixels that hit the sky.
  • Precompute. Anything that doesn't change every frame can be computed once into a buffer (Chapter 15) and read back as a texture.
// AHA

A GPU is a stadium of students doing the same sum in lockstep, each on their own pixel, each writing only their own answer. Every rule of shader programming, from "no memory" to "branches cost both sides", follows from that picture.

What you now know

  • GPUs run one small program on huge amounts of data in parallel; each pixel is independent.
  • The pipeline: vertices → vertex shader → rasterizer → fragment shader → framebuffer.
  • Shadertoy-style shaders draw one triangle that covers clip space (−1..1), so the fragment shader runs once per pixel.
  • Runners wrap mainImage with uniforms and a real main(); fragCoord is gl_FragCoord.xy.
  • Data comes in as attributes, varyings, uniforms and textures; a fragment shader writes only its own pixel.
  • Groups of 32–64 pixels run in lockstep: divergent branches run both sides, loops wait for the slowest pixel. Derivatives come from 2 × 2 quads.
  • Floats have about 7 significant digits: big numbers lose fine detail. NaN spreads and looks different on different GPUs.
Exercises

1. In precision, change the 0.001 to 0.1 and the 1000.0 to 10.0, so the ramp spans a wider range. Which strips become smooth again, and why?

Answer

All but the bottom one. The ramp now spans a range 100 times wider, so it covers 100 times more of the representable steps. Near 10,000 the steps are about 0.001 apart, so a range of 0.1 holds about 100 of them: still visibly banded on a wide screen. Precision problems are always about the ratio between the size of a number and the size of the detail you need.

2. Make a shader that shows black where iTime has been running for less than 10 seconds and white after. Is this if divergent?

3. Open Chapter 14's terrain in the workbench and halve the loop count and the octave count. How much worse does it look? Hold the result against how much faster it should run.
