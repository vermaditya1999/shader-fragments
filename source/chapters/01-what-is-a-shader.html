Before any code, three facts: a screen is a grid of tiny lights, a color is three numbers, and a graphics card can work on millions of pixels at once. A shader is the small program that sits at the meeting point of those three facts. By the end of this chapter you'll be able to read every word of your first shader.

Your screen is a grid of tiny lights

Look very closely at any screen (a magnifying glass or a phone camera zoomed all the way in works) and you'll see that the picture is made of a grid of tiny squares. Each square is a pixel, short for “picture element”. A laptop screen that is 1920 pixels wide and 1080 pixels tall has 1920 × 1080 = 2,073,600 of them.

Each pixel is not one light but three: a red one, a green one and a blue one, packed so close together that your eye blends them into a single color. A pixel shows a color by setting how bright each of its three lights is.

A color is three numbers

So a color is just three numbers: how bright the red light is, how bright the green is, and how bright the blue is. Shaders write each brightness as a number from 0.0 (off) to 1.0 (fully on). Half brightness is 0.5.

You may have seen colors written as 0 to 255, like rgb(255, 128, 0) in CSS or fill(255, 128, 0) in p5.js. That's the same idea on a different scale. To go from 0–255 to 0–1, divide by 255: 128 / 255 ≈ 0.5. Shaders use 0 to 1 because it makes math easier: multiplying two brightnesses always gives another brightness between 0 and 1, and “halfway” is simply 0.5.

Mixing light is different from mixing paint. Paint gets darker as you mix more colors in; light gets brighter, because you're adding more light. Red light plus green light makes yellow. All three at full brightness make white. All three off is black.

Shaders add a fourth number, alpha, for opacity: 1.0 means solid. On this site the canvas is always solid, so you'll always write 1.0 there and can ignore it.

Two million pixels, sixty times a second

A screen redraws itself about 60 times every second. Each redraw is a frame. If every pixel needs a color every frame, that's 2,073,600 × 60 ≈ 124 million colors per second. How does a computer keep up?

The main processor in a computer, the CPU, is like a single brilliant chef: it can cook anything, very fast, but one dish at a time. Drawing in p5.js mostly works this way: your draw() runs commands one after another, circle(…), then rect(…), then the next.

The graphics processor, the GPU, is a kitchen with thousands of simple cooks. None of them is brilliant, but they all follow the same recipe at the same moment, each on their own plate. Give every cook one pixel and the same short recipe, and a whole frame is done almost at once.

A shader is that recipe. More precisely, the kind of shader in this course is a fragment shader: a program that the GPU runs once for every pixel, to decide that pixel's color. (“Fragment” is the GPU's word for a pixel being drawn; Chapter 17 explains the difference, which doesn't matter yet.)

One function, asked by every pixel

This is the big shift from p5.js. In p5 you say where to draw: circle(200, 200, 50). In a shader you never say where. Instead, every pixel runs the same function and that function answers one question for that pixel: “what color am I?”

Because thousands of copies run at the same time, a few rules follow, and they shape everything in this course:

  • Same code for everyone. Every pixel runs exactly the same program. The only thing that differs between them is the input: each one knows its own position.
  • No talking to neighbours. A pixel can't ask what color the pixel next to it chose. They're all deciding at the same moment.
  • No memory. When a frame ends, everything is forgotten. Next frame, every pixel starts from scratch. (Chapter 15 shows the trick to get memory back.)

These rules feel like handcuffs at first. They're also the reason shaders are fast enough to draw complicated pictures 60 times a second. Most of this course is about clever ways to get what you want while following them.

You don't draw a picture. You write one rule, and every pixel applies it to itself at the same time. The picture is what the rule looks like across the whole screen.

Reading your first shader, word by word

Here's a complete shader. It runs in the preview below, and on the right in the workbench, where you can edit it.

Every pixel runs this and every pixel gives the same answer, so the canvas is one flat orange. Let's read it piece by piece.

  • mainImage is the name of the function. The program that runs your shader (the runner) looks for a function with exactly this name and calls it once for every pixel. It's like draw() in p5.js: you write it, but you never call it yourself.
  • void, written before the name, says the function doesn't hand back a value with return. Its answer leaves another way, through fragColor.
  • Inside the parentheses are the function's parameters, the things that go in and out. There are two, separated by a comma.
  • in vec2 fragCoord is the input. vec2 is a type: a bundle of two decimal numbers. fragCoord holds this pixel's position, its x and its y, measured in pixels. in means “given to you, read only”. (“frag” is short for fragment; “Coord” for coordinate.)
  • out vec4 fragColor is the output. vec4 is a bundle of four decimal numbers: red, green, blue, alpha. out means “you fill this in”. Whatever is in fragColor when the function ends becomes the pixel's color.
  • The curly braces { } hold the body: the instructions.
  • vec4(1.0, 0.5, 0.0, 1.0) builds a bundle of four numbers: red 1.0, green 0.5, blue 0.0, alpha 1.0. That's orange.
  • = stores it into fragColor. In code, = means “put the right side into the left side”, not “is equal to”.
  • The semicolon ; ends the instruction. GLSL needs one after every instruction, and forgetting one is the most common error there is.

That's the whole thing. The language is called GLSL, the OpenGL Shading Language. It looks a lot like C or JavaScript, with some rules of its own that Chapter 2 covers.

Using where you are

A flat color is boring because every pixel ignores its input. Let's use it. The canvas has a width in pixels, which the runner provides as iResolution.x. If a pixel divides its own x position by the width, it gets a number that is 0 at the left edge and 1 at the right edge:

Three new things appeared:

  • fragCoord.x reads just the x out of the two-number bundle. .y would read the y.
  • float red = …; makes a new variable. float is the type for a single decimal number, and red is a name we chose. From here on, red holds the result of the division.
  • Lines starting with // are comments: notes for humans. The computer skips them.

Say the canvas is 800 pixels wide. A pixel near the left at x = 0.5 computes 0.5 / 800 ≈ 0.0006, almost no red. A pixel in the middle at x = 400.5 gets about 0.5, half red. A pixel at the right edge, x = 799.5, gets about 0.999, full red. Dividing a position by the total length always turns it into a fraction of the way across, between 0 and 1, whatever the canvas size. That's why you'll divide by iResolution all the time.

Now each pixel gives a slightly different answer, and together they form a smooth ramp. Nobody drew a gradient. Every pixel just turned its own position into a brightness.

If you put the same idea in the green slot, using y instead of x, what will the canvas look like? Which corner will be yellow?

Red grows to the right, green grows upward, so the bottom-left corner is black (no red, no green), the bottom-right is red, the top-left is green, and the top-right is yellow, because full red plus full green light makes yellow. Here it is:

Notice that y grows upward: green is strongest at the top. That's the opposite of p5.js, where y grows downward. Shaders put (0, 0) at the bottom-left corner. Chapter 3 is all about coordinates.

A position is two numbers and a color is three numbers, so a position can be a color. Turning numbers into colors is also how you'll debug every shader you ever write.

Numbers outside 0 to 1

What if a color number goes above 1.0 or below 0.0? Nothing breaks. When the screen shows the pixel, anything above 1.0 is shown as 1.0 and anything below 0.0 is shown as 0.0. This is called clamping.

The ramp reaches full red 200 pixels from the left edge and stays there. The numbers keep growing (2.0, 3.0, …) but the screen can't show more than “fully on”. Negative numbers would all look black in the same way. Keep this in mind: when part of your canvas is flat black or flat white, the real numbers there may be much smaller or larger than you think.

On high-density (“retina”) screens, the canvas has more pixels than its size on the page suggests, often twice as many in each direction. fragCoord counts real pixels, so 200 of them can look like a short distance. That's exactly why dividing by iResolution is the habit to build: it works on any screen.

Breaking it on purpose

You'll make mistakes, so it's worth seeing what they look like while nothing is at stake. In the workbench, delete the semicolon at the end of the fragColor line. Three things happen:

  1. The line with the problem gets a red band in the editor.
  2. A box under the editor explains the error in plain words, with the compiler's original message underneath.
  3. The canvas keeps showing the last version that worked, so you never lose the picture while you fix things.

The message will say something like syntax error. Compilers often notice a missing semicolon on the line after the real mistake, because that's where they realise something's wrong. Put the semicolon back and the error disappears. Chapter 19 covers debugging in depth, and the reference has an error decoder.

Where iResolution and friends come from

You used iResolution without declaring it. Where does it come from? The runner provides it. Before every frame, the runner sets a handful of values that every pixel can read. They're called uniforms, because they're uniform: exactly the same for every pixel in a frame.

What you now know

  • A screen is a grid of pixels. Each pixel is a red, a green and a blue light, so a color is three numbers, each from 0.0 to 1.0.
  • Light adds up: red + green = yellow, all three = white.
  • A fragment shader is a function that the GPU runs once per pixel, all at the same time, to decide each pixel's color.
  • mainImage receives fragCoord (this pixel's position, in pixels, from the bottom-left) and must fill in fragColor (red, green, blue, alpha).
  • Dividing a position by iResolution turns it into a fraction from 0 to 1.
  • Colors outside 0 to 1 are clamped when shown.
  • Uniforms like iTime and iResolution are provided by the runner and are the same for every pixel.
