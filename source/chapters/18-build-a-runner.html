Shadertoy, the workbench on this site and p5.js's shader mode all do the same job: get a fragment shader onto the GPU and call it for every pixel. In this chapter you'll write that program yourself, in one HTML file with no libraries, and understand every line. Then your shaders can live anywhere: a portfolio page, a gift, a screensaver.

The plan

Chapter 17 described what has to happen. As a checklist:

  1. Make a canvas and get a WebGL2 context from it, the connection to the GPU.
  2. Write the two shaders: the tiny vertex shader for the full-screen triangle, and your fragment shader glued between a header and a real main().
  3. Compile both and link them into a program, reporting errors.
  4. Upload the triangle's three corners and tell the GPU how to read them.
  5. Every frame: size the canvas, set the uniforms, draw.

WebGL has a reputation for being verbose, and it is, but it's not deep. Most of the code is "create a thing, bind it, set it up", and the same few patterns repeat.

Step 1: a page and a context

The HTML is a full-window canvas, a box for error messages, and the shader itself stored in a <script> tag. A script tag with a made-up type like x-shader/x-fragment is ignored by the browser, which makes it a handy place to keep text that JavaScript reads later:

Then the JavaScript asks the canvas for a WebGL2 context. Think of the context as a remote control for the GPU: every WebGL call is a button on it.

Two details that bite people. #version 300 es must be the very first characters of the source, with nothing before it, not even a blank line, which is why the template strings start right after the backtick. And this runner only provides three uniforms; a shader that uses iFrame or iChannel0 will fail with "undeclared identifier" until you add them (an exercise below).

Step 3: compile and link

GPU drivers compile GLSL into the GPU's own machine code, right there in the browser. Each shader is compiled separately, then the two are linked into a program, which checks that what the vertex shader outputs matches what the fragment shader expects:

The error log counts lines from the top of the whole source, header included. Your code starts after the 6 header lines, so subtracting 6 turns the driver's line numbers into yours. Every runner does this; it's why the workbench's error messages point at the right line.

The three corners have to travel from JavaScript's memory to the GPU's. That takes a buffer: a block of GPU memory. Then the GPU needs to know how to read it: "the attribute aPos comes from this buffer, 2 floats per corner":

Notice the pattern: bindBuffer first, then calls that act on "the currently bound buffer". WebGL is a state machine: you select a thing, then operate on whatever is selected. Nearly every confusing WebGL bug is something being bound when you didn't expect it, or not bound when you did.

Step 5: uniforms and the frame loop

Uniforms are set by location, which you look up once by name. Then every frame: make the canvas's pixel count match its size on screen, tell WebGL the drawing area (viewport), set the uniforms, and draw 3 vertices as one triangle. requestAnimationFrame asks the browser to call the function again before the next screen refresh, usually 60 times a second, and passes the time in milliseconds:

The Math.min(…, 2) caps the density at 2: on a phone with 3 real pixels per CSS pixel, rendering at full density would mean 2.25 times as many pixels as at 2, for a difference you can barely see.

Step 6: the mouse

Browsers measure the pointer in CSS pixels from the top-left. Shaders want canvas pixels from the bottom-left, like fragCoord. So scale by the canvas's density and flip y. The whole runner

Here's everything assembled into one file. Download it, open it in a browser, and you'll see Shadertoy's default colors flowing. Then replace the shader in the <script id="shader"> tag with anything from this course that only uses iResolution, iTime and iMouse, and refresh.

A good first test is this card, which checks all three uniforms at once: the colors flow if iTime works, the circle is round and the squares square if iResolution works, and the dark dot follows your pointer while you drag if iMouse works.

Because the shader lives inside the HTML file, the runner works straight from your disk: double-click it, no server needed. Loading images as textures is different: browsers block a page opened from disk from reading other files, so for textures you'd serve the folder with a tiny local web server (for example python3 -m http.server in that folder) or put it online, for example on GitHub Pages.

A shader runner is about 100 lines: a context, two compiled shaders, one triangle, three uniforms and a loop. Every shader tool on the web is this, plus conveniences.

What the workbench adds

The workbench on this site is the same skeleton with more conveniences. Its source is in assets/engine.js (about 600 commented lines), and now you can read it. Its main additions:

  • Buffers (Chapter 15): two textures attached to framebuffer objects, drawn into with gl.bindFramebuffer and swapped every frame, using floating-point textures where the device supports them.
  • Sound (Chapter 16): a Web Audio AnalyserNode fills a 512 × 2 array each frame, uploaded into a texture with gl.texSubImage2D.
  • Many previews, one context. Browsers allow only a limited number of WebGL contexts per page (often 16), and a chapter has more examples than that. So all inline previews share one hidden canvas: each is rendered there in turn and copied into its own visible 2D canvas.
  • Friendly errors: the driver's message, matched against common patterns and explained in plain words.
  • The pixel inspector: gl.readPixels reads back the color under the pointer after a frame is drawn.
  • Exports: canvas.toBlob for PNGs, and canvas.captureStream with a MediaRecorder for video clips.
  • Adaptive resolution: if frames take too long, it renders fewer pixels (Chapter 17).

What you now know

  • A WebGL2 context is a remote control for the GPU; WebGL is a state machine of "bind, then act".
  • A runner compiles a vertex shader and your glued fragment shader, links them into a program, and reports errors with corrected line numbers.
  • The triangle's corners go into a buffer; an attribute pointer says how to read them.
  • Each frame: match the canvas's pixel size to the screen, set the viewport and uniforms, draw 3 vertices.
  • Mouse coordinates need scaling to canvas pixels and flipping to bottom-up.

1. Add iFrame to your runner: declare it in the header, count frames in JavaScript, and set it with gl.uniform1i.

2. Add a pause: pressing the space bar should freeze time, and pressing it again should continue from the same moment (keep your own clock instead of using ms directly).

3. Load an image into iChannel0. You'll need gl.createTexture, gl.texImage2D with an Image object once it has loaded, gl.texParameteri for filtering, and gl.uniform1i to tell the sampler which texture unit to use. (Serve the folder with a local web server, as the note above explains.)

4. The big one: add a Buffer A pass with ping-pong textures, so Chapter 15's examples run in your runner. Read how _makeTargets and render in assets/engine.js do it.
